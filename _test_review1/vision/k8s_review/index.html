    ❌ CRITICAL ISSUES (Must Fix Before Any Work Begins)

    1. Ollama StatefulSet InitContainer — Broken Design (§3.1, lines 100-120)

    Problem: The initContainer tries to curl http://ollama:11434/api/pull before Ollama exists. Chicken-and-egg failure. - ollama:11434 resolves to the Service, not localhost in the pod. - Even if fixed to localhost:11434, Ollama isn’t running yet.

    Fix: 

    initContainers:
  - name: model-init
    image: ollama/ollama  # Same image, not curlimages/curl
    command: ["ollama", "pull", "qwen2.5-coder:7b", "deepseek-r1:8b"]
    volumeMounts:
      - name: models
        mountPath: /root/.ollama
    env:
      - name: OLLAMA_HOST
        value: "0.0.0.0"

    Why: Pull models directly via CLI before the main container starts. Uses the same volume.

    2. GPU Sizing Inconsistency (§7.1 vs §13.1)

    Problem: §7.1 says vision models need 24 GB VRAM (RTX 4090), but §13.1’s cost table uses g4dn.xlarge (16 GB VRAM). - Cannot run qwen2.5-coder:7b (4 GB) + deepseek-r1:8b (8 GB) + vision model (8 GB) on 16 GB.

    Fix: - Option A: Update cost table to g4dn.2xlarge (32 GB VRAM, ~$800/mo). - Option B: Clarify that not all models run simultaneously (mutually exclusive loading).

    3. Health Checks in Phase 0 — Technically Invalid (§16.1)

    Problem: Phase 0 claims "pgrep for daemons" as a health check. pgrep is a shell command, not a K8s probe. - K8s only supports: httpGet, tcpSocket, exec (command), or grpc. - exec with pgrep might work, but pgrep returns non-zero if process not found → probe would fail.

    Fix: 

    # For non-HTTP services (e.g., healer-agent):
livenessProbe:
  exec:
    command: ["sh", "-c", "pgrep -x healer-agent >/dev/null"]
  initialDelaySeconds: 30
  periodSeconds: 10

    But better: Use HTTP if possible (add /healthz endpoint).

    4. Healer-Agent Security Risk (§3, §10)

    Problem: Healer needs Docker socket access → full host compromise risk. - §10.2 acknowledges this but only labels it baseline (should be documented as a high-risk exception).

    Fix: 1. Restrict the socket mount to only the healer-agent’s namespace: 

    volumes:
  - name: docker-sock
    hostPath:
      path: /var/run/docker.sock
    2. Add a SecurityContext to drop capabilities: 
    securityContext:
  capabilities:
    drop: ["ALL"]
  runAsNonRoot: true
  readOnlyRootFilesystem: true
    3. Audit trail: Log all Docker commands executed by healer.

    5. Missing Model Registry Strategy (§3.1, §7)

    Problem: No plan for model versioning or synchronization across Ollama pods. - If Ollama pod restarts, models must re-download (20 GB × N nodes = slow). - No mention of private model registries (e.g., for fine-tuned models).

    Fix: - Add a model cache PVC (shared across pods, ReadWriteMany if possible). - Use Ollama registry (ollama pull from a private registry). - Document model preloading in initContainers.

    6. Agent Fabric Coordination — Underspecified (§8.2)

    Problem: No details on how agents communicate or share state. - Explorer, healer, daemon need to coordinate (e.g., for drift detection). - Current Compose uses shared host networking — won’t work in K8s.

    Fix: - Phase 1 (k3d): Use HTTP + shared ConfigMaps (simple, works for ≤3 agents). - Phase 3: Use gRPC + headless Service (for inter-pod communication). - Phase 4: Use NATS/Kafka (for cross-cluster). - Add to §8.2:

apiVersion: v1

kind: Job
metadata:
  name: cherenkov-validate-{{UUID}}

  template:

      containers:
        - name: cherenkov

    Problem: The cherenkov-ebs StorageClass lacks: - volumeBindingMode: WaitForFirstConsumer (required for dynamic provisioning in multi-AZ clusters). - No encryption (EBS should be encrypted by default).

    E0.5e — Discriminating power of the baseline-free integrity oracle

    Date: 2026-07-30 Question: can CHERENKOV detect a weakened test suite from the spec alone, with no known-honest baseline to diff against? Why it matters: cherenkov check-suite requires --baseline. A stranger auditing their own repo does not have one — that is their situation, not an oversight. Baseline-free detection is the difference between a tool you adopt and a tool you can be shown.

    Method

    Ground truth is the project's own labelled corpus, demos/catch-the-ai-cheating/ts:

    fixture label
    suite_good.spec.ts honest
    suite_cheat_weakened.spec.ts cheating — matchers loosened (toBe(200) → toBeLessThan(500))
    suite_cheat_deleted.spec.ts cheating — assertions removed
    suite_cheat_hallucinated.spec.ts cheating — asserts a field the spec never documents

    Each suite was executed with the real PlaywrightRunner against a BrokenImplServer routed per path (/orders/42 → success, /orders/999 → 404), perturbing one axis at a time of the documented 200 response.

    A suite that passes a deliberately-broken API is vacuous — that is the detection signal.

    First attempt was unsound and its result discarded. Serving one response for every path broke the honest suite's not_found test, which needs a 404. The honest suite failed the control, so the recall figure it produced (0.00) measured the harness, not the oracle. Per-path routing fixed it. Recorded here because the failure mode is easy to repeat.

    Result

    PASS = suite passed the mutant = flagged vacuous.

    mutant good weakened deleted hallucinated
    control — conforming PASS PASS PASS fail
    status only, 200→201 fail PASS fail fail
    field only, drop id fail fail fail fail
    value only, total→0 fail fail PASS fail
    enum only, status→"void" fail PASS PASS fail
    coarse — status + dropped field (ships today) fail fail fail fail

    Readings

    1. The coarse mutation that ships today detects nothing. All three cheating suites fail it, so all three are scored "assertions are meaningful" — including the deliberately weakened one, which is the exact case the gate exists to catch. It perturbs status and drops a field simultaneously, so any test that trips over either reads as strong. Failure cannot be attributed.

    2. Isolated single-axis mutants detect everything. status-only catches weakened; value-only catches deleted; enum-only catches both. Coverage requires a battery, not one mutant — no single axis catches every cheat.

    3. Hallucination needs no mutant at all. It fails the conforming response, because it asserts something the API never returns. The existing prism-dryrun gate already covers this channel.

    4. field drop id has no signal. The honest suite fails it too, so nothing is attributable. Dropping a required field is too blunt to discriminate.

    Combined, isolated mutants plus the conforming run cover 3/3 cheat classes with 0 false alarms on the honest suite.

    Correction — where the base response comes from (2026-07-30)

    The table above was produced with the honest response (id: 42, total: 99.5, status: "paid") supplied by hand. Implementing the battery as shipped code exposed why that matters: those values came from reading the honest test, not from the spec.

    Driving synthesize_mutant_battery() with a schema-sampled body instead gives {"id": 1, "total": 1.0, "status": "paid"} — correct types, arbitrary values — and the honest suite then fails the conforming control, because it asserts toBe(42) and toBe(99.5). Every verdict below a failing control is meaningless.

    base response honest suite passes control? usable?
    schema-sampled no no — all verdicts void
    recorded from the target yes yes — 3/3 caught, 0 false alarms

    A spec constrains types, not instance values. So a baseline-free audit cannot be spec-only; it must be record-then-perturb:

    1. run the suite against the real target and capture each response, confirming the suite is green — that is the control
    2. replay each test against the recorded response with one axis perturbed
    3. a test that still passes is blind to that axis

    This needs no known-honest baseline suite — only a live target, which verify already requires. synthesize_mutant_battery(..., base=(status, body)) takes the recorded response; omitting base falls back to schema sampling, which is sound only inside the repair loop's closed prism path, where the test was written against the same mock now serving it.

    Re-run with a recorded base, using shipped code rather than the scratch harness: 3/3 cheat classes detected, 0 false alarms. enum was the strongest single mutant (caught both weakened and deleted); missing produced no signal at all, since the honest suite fails it too.

    Record-then-perturb, end to end (2026-07-30)

    The correction above still fed the recorded response in by hand. RecordingProxy (cherenkov/verdict/traffic_capture.py) closes that: point the suite's API_URL at it, and every request is forwarded to the real target while the response is captured.

    Run against a live local Orders server, with no hand-supplied values anywhere — the audit discovers everything at runtime:

    1. RECORD   each suite through the proxy against the live target
            recorded base for /orders/42: (200, {'id': 42, 'total': 99.5, 'status': 'paid'})
            green: good yes · weakened yes · deleted yes · hallucinated NO

2. PERTURB  battery built from the RECORDED response
            conforming 200 {'id': 42, 'total': 99.5, 'status': 'paid'}
            status     201 {'id': 42, 'total': 99.5, 'status': 'paid'}
            value      200 {'id': 0,  'total': 99.5, 'status': 'paid'}
            enum       200 {'id': 42, 'total': 99.5, 'status': 'cherenkov_not_in_enum'}
            missing    200 {'total': 99.5, 'status': 'paid'}

3. REPLAY   mutant      good   weakened  deleted  hallucinated
            conforming  PASS   PASS      PASS     fail
            status      fail   PASS      fail     fail
            value       fail   PASS      fail     fail
            enum        fail   PASS      PASS     fail
            missing     fail   fail      fail     fail
    cheat class caught by
    weakened status, value, enum
    deleted enum
    hallucinated the green run itself — it fails the real API, no mutant needed

    3/3 detected, 0 false alarms on the honest suite.

    Worth noting: hallucination is caught before any mutation, because a suite asserting a field the API never returns cannot pass against the live target. The green run is therefore both the control and a detector.

    What is proven, and what is not

    Proven: the mechanism. Recording, battery synthesis and replay compose into a working baseline-free audit using only shipped components and a live target.

    Not yet built:

    • A CLI surface. There is no cherenkov audit; this is a harness over library calls.
    • Path/response correlation at scale. The demo has one endpoint. Real suites hit many paths with parameterised values, so mapping each test to the response it depends on needs work.
    • State-mutating suites. recorded_base() takes the most recent response per path; a suite whose POST changes what a later GET returns needs sequence-aware replay, not a flat map.
    • Cost. N mutants means N replays per test. Fine for an audit command, too slow per repair-loop candidate.

    Consequences

    A defect in a shipped gate. ReviewStage._gate_meaningful_assertion uses the coarse mutant from mutant_synth.synthesize_mutant_response(). On this corpus it would pass a weakened suite as meaningful. Its docstring cites toBeLessThan(500) as the case it prevents — that is precisely the assertion in suite_cheat_weakened, and it is not caught.

    The wedge is feasible but not one command away. A baseline-free audit works, and needs:

    • a mutation battery — status, single-value, enum — each served in isolation → shipped as synthesize_mutant_battery()
    • a recorded base response from the live target, not a schema sample (see the correction above) → the base argument
    • a conforming-run precondition, so "failed the mutant" is attributable to assertion strength rather than an unrelated error
    • per-mutant reporting, so the user is told which assertion is weak
    • still to build: the record step — capture responses during a green run and feed them to the battery. This is the remaining gap between the primitive and a product.

    That is real work with a latency cost (N runs per test instead of 1), and needs a decision on where it runs: the repair loop cannot afford a battery per candidate, an audit command can.

    Limits of this evidence

    One API, one endpoint, three cheat fixtures, hand-authored by this project. Directionally strong, not a benchmark. Before any external claim:

    • widen to ≥10 third-party specs (E0.5d)
    • add cheat classes not represented here — timing assertions, error-path-only suites, snapshot tests
    • measure false-alarm rate on honest suites at scale, which is what makes an auditor trustworthy or unusable

    Reproduction

    Harness: isolated_mutants.py (scratchpad; promote into demos/catch-the-ai-cheating/ when the battery lands). Composes shipped parts only — synthesize_mutant_response, BrokenImplServer, PlaywrightRunner.
